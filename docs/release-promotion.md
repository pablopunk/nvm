# Release promotion

Nevermind builds platform artifacts for a selected `main` commit and records the version, source commit, workflow run, and SHA-256 hashes in a manifest. Dev prereleases use `v<version>-dev`; their binary version is the numeric version in the tag. Commit identity is provenance, not part of version ordering. Dev builds are retained for 30 days; the newest, pointer-targeted, stable-referenced, and explicitly preserved builds are retained longer. Promoted nightlies hold independent asset copies, follow the same 30-day window, keep their newest build and pointer targets, and do not keep their source dev build alive. Add a standalone `Nevermind-Preserve: true` line to a dev release's notes to preserve it.

Versions use `YYYY.MMDD.N`, where the date is UTC and `N` is the build sequence for that day. For example, `2026.1031.1` is the first allocated build on October 31; January 5 is written `2027.105.1` because SemVer numeric components cannot have leading zeroes. The serialized dev workflow allocates the next number from existing release tags, reuses an eligible draft on retry, and skips rebuilding an already published source commit. Abandoned drafts or tags can leave gaps. During the transition, existing versions on the same day set the minimum sequence so updates never move backwards; the counter resets the following UTC day. A future-dated tag stops allocation until investigated.

Nightly and stable promotions copy the selected dev packages and blockmaps without rebuilding or re-signing. Their releases hold independent asset copies. Nightly uses `v<version>-nightly`; stable uses `v<version>` and publishes as GitHub's latest stable release. Stable updater metadata is copied to the `latest` channel filenames; the referenced package bytes remain unchanged. Drafts are verified before publication. Promotion requires successful CI and a healthy production backend serving the selected commit or a verified main descendant.

PR CI runs checks and tests without the full release package matrix. The hourly dev workflow builds and validates those packages on `main`; a failed build cannot reach its publication job. OpenCode's repair workflow also handles failed scheduled or manually dispatched dev builds, using the recorded build source and failed logs. It stops if the source or logs are unavailable, if the source has been superseded, if no fix is produced, or if the repair limit is reached; investigate the failed run and credentials or service failures manually. A successful repair goes through main CI, and the next hourly dev build verifies packaging again.

To promote stable, dispatch `promote-stable.yml` with the retained dev tag. Inspect the selected release, prior stable release, source history, CI, and backend compatibility before dispatch. The legacy tag-driven release jobs refuse a tag that sorts below the latest stable release, and the manual nightly workflow only performs dry runs. Workflow failure is not publication success. Check the run and release, exact asset set and hashes, tag commit, notes, and updater metadata after publication. A packaged updater journey and external user validation are separate checks.

The dev build, promotion, and retention workflows serialize publication operations. A failed draft can be retried only if its source and promotion provenance match; a conflicting published release or tag must not be overwritten. Investigate orphan tags and partial drafts before intervening. Do not delete a release or tag merely to make a retry pass.

Published dev and nightly releases are discovered through small public files on the `release-pointers` branch. Pointer updates happen after the release assets have been verified and published, retain the previous target as a fallback, and refuse to move backward. Updater reads use the public raw file endpoint with cache bypass; stable discovery still uses GitHub's latest stable release. If pointer publication fails after a release is published, the next unchanged dev run or nightly run repairs it. Retention fails closed if the dev pointer cannot be read and preserves both of its targets.

Switching channels can move to an older build, but only under the state compatibility contract below. Released builds that predate it keep their own updater behavior and never downgrade.

## macOS architecture

New releases support Apple silicon (arm64) only. Intel Macs cannot run these releases and should remain on their last compatible version or move to an Apple silicon Mac. On Apple silicon, replace an Intel copy running under Rosetta with the arm64 ZIP from the release page: quit Nevermind, download the `mac-arm64.zip`, and replace the app in Applications. Back up your Nevermind data before replacing the app. Existing Intel builds may advertise an update they cannot install; manually choose the correct package instead. New promotion validation requires the arm64-only asset set and will reject older retained dev builds containing Intel assets.

## State compatibility boundary

The host persists more than `state.json`. A downgrade contract must account for portable configuration, AI chats and image files, learning records, clipboard images, extension windows and drafts, extension storage and secrets, extension source files, account tokens and BYO credentials, and persisted dictation recordings. Cache and diagnostic files have different recovery requirements, but their readers must also tolerate any format left by a newer build. The extension host can run user-provided extension code that mutates its own storage and source independently of application upgrades.

A target's version alone does not prove it can read these stores. Missing, corrupt, or unverifiable compatibility information blocks a downgrade; selecting a channel must not cause an older binary to overwrite data from a newer incompatible writer. The state loader advances durable private and shared compatibility high-water markers before loading host state and refuses a newer epoch or a missing marker in one of the two roots. Unmarked profiles remain untrusted, including empty profiles. Release metadata carries the build's `nevermindStateEpoch`; release workflows stamp it from `src/app/resources/state-compatibility.json`. Increment that epoch before a host-owned persisted format becomes unreadable by earlier builds.

### Authorizing an older build

The updater lets electron-updater report older builds, then withholds them until the host authorizes the target: both state roots must be trusted, free of a pending update, and carry a high-water epoch equal to the target's advertised epoch. An older build is never downloaded automatically, including by dev-channel auto-download and manual checks. Explicit download and the final install each recheck authorization, so a marker that changes afterward revokes the install. The Updates view says when an older build is withheld and why.

Trust is established only by the Updates view action "Back Up and Verify State". It is rendered with a host-owned confirmation and starts a maintenance transaction: the interactive entry points, background jobs, extension storage, and portable configuration pause and drain; pending user state, learning records, and drafts flush; the shared-state lease is taken; a verified backup of both roots is written to a sibling `nevermind-state-backups` directory; and the markers are marked trusted. The transaction fails closed, resumes the paused writers, and leaves state untrusted if the backup changes while it is being read, this process does not hold the shared-state instance lock, or an update install is in flight. Persisted writes that start outside an interactive request, such as secret files and dictation recordings, go through the same pause, and scheduled user-state saves wait until the backup has been read. Backups hold credentials and are not pruned automatically. Quit requests wait for a transaction that already holds the lease and a transaction that has not taken it refuses to start, so a normal quit cannot strand the lease; a crash, force-quit, or power loss during the transaction can. Startup then fails with a lock-recovery error on systems without owner-exit proof. After confirming no Nevermind process is running, remove the `<shared-root>.writer-lock` directory next to the shared state root to recover.

The transaction cannot detect a Nevermind build that predates the shared-state instance lock, so the action's wording asks the user to quit older instances first. Extension code can also write its own storage and source independently; the backup's change detection catches a write that races the copy but the pause does not stop it. Marker updates hold an exclusive shared-state lease. The lease never takes over based on elapsed time, because a suspended writer can still resume. Automatic recovery requires a matching boot and PID namespace and confirmation that the recorded process no longer exists; an unidentifiable or inaccessible owner remains locked. On systems without that proof, recovery requires an explicit, separately verified procedure. The lease is not proof that legacy instances or unrelated shared-state writers have stopped.

CI cannot prove a packaged installer accepts an older version on each platform, OS permission behavior, or a real user's profile migration. Those remain separate journeys.
